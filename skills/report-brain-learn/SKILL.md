# 보고서 브레인 학습

보고서 브레인은 혁신팀장의 기획보고서 작성 방식을 학습한 지식 저장소다. 나성의현인(guru-brain)과 같은 구조다. 재료(문서 노트)와 합성(페르소나·충돌 규칙)을 나누고, 소스를 흡수할 때마다 버전을 올린다. 구조와 노트 형식은 `references/architecture.md`에 있다. 작업 전에 반드시 읽는다.

브레인 문서는 모두 Google 문서다. Markdown으로 올리면 frontmatter가 한 줄 제목처럼 변환되므로, 버전·ID 같은 기계용 값은 `_index` 본문에도 반드시 적는다. 현재 버전은 `_index`의 "현재 버전" 절이 기준이다. 어떤 문서가 어디 있는지는 루트의 `_index` 문서가 정한다. 문서를 새로 만들거나 버전을 올리면 `_index`도 반드시 고친다. `_index`가 틀리면 작성 스킬이 브레인을 못 읽는다.

## 작업 종류

사용자 요청을 아래 넷 중 하나로 고른다.

1. **문서 흡수**: 새 보고서 1건~여러 건을 학습.
2. **맥락 갱신**: 청장 말씀·국무회의·지침 등 최근 메시지를 `context/context-current`에 반영. 버전은 올리지 않는다.
3. **전체 재합성**: 흡수 기록 전부를 다시 읽고 페르소나를 처음부터 다시 쓴다. 흡수 문서가 10건 쌓일 때마다, 또는 사용자가 요청할 때.
4. **피드백 반영**: 사용자가 브레인으로 쓴 결과물을 고친 내역을 받아 규칙에 반영.

## 1. 문서 흡수

### 1-1. 대상 확인
- 사용자가 파일을 지정하지 않았으면 `reading-log`에 없는 코퍼스 파일을 찾아 목록을 보여 준다(코퍼스 폴더 최근 파일 검색).
- 대외비 표시 문서는 흡수하지 않고 `reading-log`에 "제외(대외비)"로 적는다.

### 1-2. 읽기
- HWP·HWPX: Drive `download_file_content`로 받아 kordoc으로 Markdown 변환(`references/kordoc.md`). 받은 파일은 작업 폴더의 빈 하위 폴더에 두고, 끝나면 지운다.
- PDF·docx·Google 문서: `read_file_content`.
- 다운로드 한도는 10MB다. 5MB가 넘는 파일은 다운로드 응답이 커서 커넥터 연결이 끊길 수 있다. 5MB 넘는 HWP는 사용자에게 PDF로 저장해 올려 달라고 한다.
- 반대로 아주 작은 HWP(대략 50KB 미만)는 응답이 파일로 저장되지 않고 대화에 base64로 바로 들어온다. 이걸 손으로 옮겨 디코드하지 않는다(전사 오류). 이런 파일도 PDF로 올려 달라고 한다.
- 정리하면 HWP는 50KB~5MB 구간만 안정적으로 읽힌다. 그 밖은 PDF가 안전하다.
- DRM·암호 문서는 읽지 못한다. 사용자에게 알리고 건너뛴다.

### 1-3. 문서 노트 작성
- `references/architecture.md`의 9절 형식 그대로. 신뢰 표식 `[확인 위치]`·`[재구성]`·`[추정]`을 단다.
- 요약하지 않는다. "이 사람이 이 문서를 어떻게 썼나"를 뽑는다: 꼭지 구조와 순서 논리, 제목 패턴, 문장틀·서술어, 상위 메시지 배치, 판단 순간.
- 같은 유형 노트가 이미 있으면 그 노트와 비교해 "이번에 달라진 점"을 9절 시점 표식에 적는다.
- 개인 실명·전화번호·납세자 정보·직원 인적사항은 넣지 않는다. 직위만 쓴다. 청장 이름처럼 공개된 기관장 이름은 허용.
- 원문 긴 인용 금지. 예시는 한 줄 이내.

### 1-4. 렌즈 갱신
- 말씀자료·보도자료면 `lens-청장`, 상급기관 지침이면 `lens-상급기관`, 국실 취합 자료면 `lens-국실`을 고친다.
- 렌즈 문서는 덮어쓰지 않고 해당 절에 추가한다. 맨 위 `updated:` 날짜를 고친다.

### 1-5. 흡수 기록
`synthesis/absorb/<YYYYMMDD>-<묶음명>` 문서를 만든다.

```markdown
---
source_type: 문서 | 묶음
sources: [<노트 이름>, …]
absorbed_at: YYYY-MM-DD
version_before: vX
version_after: vY (변경 없으면 vX)
---
# 흡수 기록 — <묶음명>
## 핵심 습득 (3~7개)
## 기존 철학과의 관계
- 강화: <기존 규칙·패턴 중 이번 문서가 다시 확인한 것>
- 충돌: <기존과 다른 것. 어느 쪽이 맞는지 조건>
- 신규: <처음 나온 패턴>
## 철학 반영
- 바꾼 곳: <보고서브레인의 절, conflict-rules의 CR-NN>
```

### 1-6. 철학 반영과 버전
1. 바꿀 것이 없으면(강화만 있으면) 버전을 올리지 않는다. 흡수 기록과 노트만 남긴다.
2. 판단 프로세스·유형별 뼈대·문체 규칙·충돌 규칙 중 하나라도 바뀌면 minor(+0.1). 예시·표현만 바뀌면 patch(+0.0.1).
3. 순서: 현재 `synthesis/보고서브레인`을 그대로 `versions/vX` 문서로 보존돼 있는지 확인 → `보고서브레인` 수정(frontmatter `version`, `sources` 갱신) → 새 버전 내용을 `versions/vY` 문서로 새로 만든다. 스냅샷은 만든 뒤 고치지 않는다.
4. 충돌이 새로 생기면 `conflict-rules`에 CR-NN을 추가한다. 형식은 `references/architecture.md`.

### 1-7. 색인과 로그
- `_index`에 새 노트·흡수 기록·스냅샷의 이름과 파일 ID를 추가한다. 현재 버전 줄을 고친다.
- `reading-log`에 문서명, 노트 이름, 날짜, 상태를 추가한다.
- 흡수 문서 누적이 마지막 재합성 이후 10건을 넘으면 사용자에게 전체 재합성을 권한다.

## 2. 맥락 갱신

- 사용자가 붙여 넣은 청장 말씀, 국무회의 발언, 새 지침, 또는 웹 검색 결과를 `context/context-current`에 추가한다. 형식은 문서 안 "최근 발언 로그" 절을 따른다.
- 원문 표현을 그대로 보존한다.
- 문서 맨 위 작성일을 오늘로 고친다.
- 새 지침 파일이면 코퍼스 `08_상급기관지침`에 올리라고 권하고, 올라오면 1번 흡수로 처리한다.

## 3. 전체 재합성

1. `absorb/` 기록 전부와 렌즈 3개, `conflict-rules`를 읽는다.
2. 최근 흡수에 쏠리지 않게, 유형별로 최소 1개 노트를 다시 연다.
3. `보고서브레인`을 처음부터 다시 쓴다. 이전 버전과 비교표(무엇이 남고 바뀌고 빠졌나)를 흡수 기록에 남긴다.
4. minor 버전을 올리고 스냅샷을 만든다.

## 4. 피드백 반영

- 사용자가 "브레인이 쓴 것을 이렇게 고쳤다"고 주면, 고친 전후를 비교해 패턴을 뽑는다.
- 한 번의 수정은 `absorb/`에 "피드백" 기록으로만 남긴다. 같은 종류 수정이 두 번 이상 쌓이면 규칙으로 올리고 버전을 올린다. 한 번의 취향을 규칙으로 굳히지 않기 위해서다.

## Drive에 쓰는 방법

- 새 문서: `create_file`에 `title`, `parentId`, `textContent`(Markdown), `contentMimeType: "text/markdown"`. Google 문서로 변환된다. 변환이 실패하면 `text/plain`으로 다시.
- 기존 문서 내용 수정: 커넥터에 내용 수정 기능이 없다. 새 내용으로 같은 제목 문서를 만들고, 옛 문서는 `trash_file`로 휴지통에 넣고, `_index`의 ID를 새 것으로 바꾼다. `versions/` 스냅샷은 절대 이렇게 바꾸지 않는다.
- 문서 하나에 넣는 내용이 너무 크면 커넥터 연결이 끊길 수 있다. 문서 하나는 2만 자 안쪽으로 유지한다.

## 끝나면 보고

- 흡수한 문서와 만든 노트 이름.
- 버전 변화(vX → vY)와 바뀐 규칙 한 줄씩. 안 바뀌었으면 "버전 유지, 강화만".
- 읽지 못한 문서와 이유.
